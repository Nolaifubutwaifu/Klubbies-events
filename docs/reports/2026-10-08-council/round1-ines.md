# Round 1: Ines (Accessibility and Visual Craft)

**Verdict.** The token system is unusually disciplined: real contrast comments, a 3:1 input edge, 44px buttons, reduced-motion guards on almost every animation, and a correct focus-trapped menu on the marketing site. Most screens are close to WCAG 2.2 AA.
The failures cluster where the product is most used and least tested with a keyboard. The shared `Dialog` takes focus away whenever its parent re-renders, so you cannot type into the "Paste a guest list" box. The photo viewer leaves the page behind it focusable, its sheets are not dialogs, and its focus ring is 2.65:1 on near-black, or 1.06:1 for an event that picked the ink swatch.
Fix the five focus findings first (I-1 to I-5); all are S/M effort. After that, one caption token fails on sand (4.43:1), and there is some token drift (no danger token, an undefined `--kb-mist`, a retired salmon error page).

Contrast ratios below come from the WCAG 2.x relative-luminance formula, run on the actual hex values in `app/globals.css` and `lib/theme.ts` (script in my scratch folder). Where I say "event accent", I ported `eventToneStyle()` and ran all ten `ACCENT_SWATCHES` through it.

### I-1 `Dialog` steals focus on every parent re-render: you cannot type a guest list
- **Where:** `components/Dialog.tsx:20-30` (effect depends on `[open, onClose]`; cleanup calls `previous?.focus()`, then the re-run focuses the first `input, button…`, which is the ✕ at :45 because it comes first in the DOM). Every caller passes an inline arrow, e.g. `app/(app)/admin/[handle]/attendees/RosterImport.tsx:179` and :208, `components/AlbumGrid.tsx:323`. Organiser, Attendees › "Paste a list instead", and "Check the columns".
- **Heuristic / severity / effort:** bug + WCAG 2.1.1 Keyboard, 2.4.3 Focus Order; Nielsen #3 user control. **Sev 3**, effort **S**.
- **Problem:** In the paste dialog, `onChange` calls `setPasted`, which re-renders `RosterImport` and creates a new `onClose`. The effect then tears down: focus jumps to the "Paste a list instead" button behind the backdrop and then to ✕. The organiser types "M" and every keystroke after that lands on Close. A paste works once, and then focus is on ✕, so Enter closes the dialog and the text is gone. In "Check the columns", each arrow-key change of a `<select>` throws focus to ✕. The dialog also has no Tab trap, so Tab walks into the page behind it, even though it says `aria-modal="true"`. The marketing `SiteNav` (`components/site/SiteNav.tsx:39-51`) already traps Tab correctly, so the two modals behave differently (Nielsen #4).
- **Fix:** Keep `onClose` in a ref (`const close = useRef(onClose); close.current = onClose`) and make the effect depend on `[open]` only. Give initial focus to the first control in the *body* (a `data-autofocus` attribute, else the first field, else the primary action), not the ✕. Add the same Tab wrap as SiteNav, or set `inert` on the app root while open. Use `aria-labelledby` pointing at the `<h2>` instead of a duplicate `aria-label`.

### I-2 The lightbox leaves the page behind it focusable and hidden (2.4.11)
- **Where:** `app/(app)/e/[handle]/layout.tsx:89-95` renders `AppHeader`, then the viewer, then `CreditLine`. `app/(app)/layout.tsx:12-13` adds `AppFooter`. The viewer layout is only a `fixed inset-0 z-40` cover (`app/(app)/e/[handle]/a/[albumId]/[mediaId]/layout.tsx:8`). `MemberTabBar.tsx:15-16,67` knows it is in the lightbox and hides itself; `AppHeader` does not. Attendee, photo viewer.
- **Heuristic / severity / effort:** WCAG **2.4.11 Focus Not Obscured (Minimum)** (new in 2.2, AA), 2.4.3, 1.3.2. **Sev 3**, effort **S**.
- **Problem:** Shift+Tab from "Close photo" moves into the event switcher, header nav and account menu, all painted over by the z-40 cover. Tab past "More" moves into the credit line and footer links. Focus is *entirely* hidden, which is exactly what 2.4.11 forbids. Screen-reader users also hear the full header before and after every photo.
- **Fix:** Render the viewer route without the event chrome: a route group whose layout skips `AppHeader` and `CreditLine`, or `AppHeader` returning null in the lightbox the way the tab bar does. Short of that, set `inert` on the header, credit line and footer while the viewer is mounted.

### I-3 The viewer's "More" and "Request removal" sheets are not dialogs
- **Where:** `Viewer.tsx:318-378` (More sheet), :357 (opens the removal sheet), :380-414 (removal sheet), :154 (Escape). Attendee, viewer › More › Copy link, "This isn't me", Request removal.
- **Heuristic / severity / effort:** WCAG 4.1.2 Name, Role, Value; 2.4.3 Focus Order. **Sev 3**, effort **M**.
- **Problem:** Each sheet is a plain `div`: no `role="dialog"`, no name, no focus move, no focus return. Opening More leaves focus on the More button, and a screen reader announces nothing. Choosing "Request removal" unmounts the button that had focus, so focus falls to `<body>` (the top of the document) at the moment of a sensitive action. Escape closes the sheet but does not return focus. Removal is the privacy flow, so it is the worst place to lose a keyboard or VoiceOver user.
- **Fix:** Build both sheets on the fixed `Dialog` (I-1) with a `variant="sheet"` that keeps today's bottom-sheet styling. Focus the first action on open and return focus to More on close. Name them with their `<h2>` ("About this photo", "Take this one down?").

### I-4 The focus ring disappears on every dark surface
- **Where:** One global ring, `app/globals.css:179-182` (`2px solid var(--kb-ember)`). Dark surfaces: the viewer `#14100f` (`[mediaId]/layout.tsx:8`, `Viewer.tsx:183`); the selection bar `bg-ink` (`AlbumGrid.tsx:176`); `UndoBar.tsx:50` (`bg-ink`); `.kb-ink-band` and `.btn-on-dark` (`globals.css:205-213, 410-418`), used on Features › Privacy (`app/(marketing)/features/page.tsx:64-82`). Attendee viewer, album selection, organiser undo, marketing.
- **Heuristic / severity / effort:** WCAG 1.4.11 Non-text Contrast (focus indicator), 2.4.7 Focus Visible. **Sev 3**, effort **S**.
- **Problem (measured):** Default ember on the lightbox is **2.65:1**, and on ink it is **2.49:1**. Per-event accents on the lightbox: purple `#7e22ce` 2.71, rose `#be123c` 3.01, and the ink swatch `#16181d` **1.06:1**, which is invisible. Keyboard users browsing photos cannot see whether they are on Close, Previous, Next, a filmstrip thumb, Save, Download or More.
- **Fix:** Add a `--kb-focus` / `--kb-focus-on-dark` token pair. On dark containers (`.kb-dark` on the viewer root, ink band, selection bar, undo bar) set `:focus-visible { outline-color: #fff }` (18.9:1 on `#14100f`). Better still, use a two-tone ring everywhere (`outline: 2px solid var(--kb-ember); box-shadow: 0 0 0 4px #fff`) so it holds on any photo or accent.

### I-5 Inline `outline` styles override the focus ring (colour swatches, selected tiles), and swatches are named by hex
- **Where:** `app/(app)/admin/[handle]/settings/SettingsForm.tsx:78` (`aria-label={\`Use ${swatch}\`}`), :84 (`outline: … : "none"` inline), :81 (32×32). `components/AlbumGrid.tsx:293` (inline outline on selected tiles). Organiser, Settings › Brand colour; anyone selecting photos.
- **Heuristic / severity / effort:** WCAG 2.4.7 Focus Visible, 2.4.6/1.1.1 (meaningful names), 4.1.2. **Sev 3**, effort **S**.
- **Problem:** An inline `outline: none` beats the stylesheet's `:focus-visible`, so tabbing across the nine unselected swatches shows **no focus at all**. The selected swatch, and a selected tile in select mode, wear a permanent outline that looks the same as focus, so you cannot tell "selected" from "focused". A screen reader reads the swatches as "Use hash zero e seven four nine zero, toggle button", which tells nobody which one is teal.
- **Fix:** Move selection styling to a class or `aria-pressed` selector and never set `outline` inline. Draw selection with a ring and the existing tick (for tiles, add a tick badge). Give the swatches names ("Blue", "Teal", "Green"… "Ink") and wrap them in a `role="radiogroup"` with radios, so arrow keys work and the state is announced. Bump them to 44px on `pointer: coarse` (see I-13).

### I-6 Album tiles hide their status from screen readers
- **Where:** `components/AlbumGrid.tsx:145-149` (`labelFor`), :301 and :291 (`aria-label` on the link/button), :28-51 (inner "Cover", "Processing", "Failed", video duration), :41 (`aria-label="Saved"` on a plain `<span>`). Attendee and organiser, album grid.
- **Heuristic / severity / effort:** WCAG 1.3.1 Info and Relationships, 4.1.2. **Sev 2**, effort **S**.
- **Problem:** `aria-label` on the link replaces all of its content, so "Cover", "Processing", "Failed" and "0:42" are never announced. `aria-label` on a role-less span is prohibited and ignored, so "Saved" is silent too. An organiser using VoiceOver cannot find the failed uploads, and an attendee cannot tell which photos they have saved.
- **Fix:** Build the label from the state: "Video 3 of 110 in Awards night, 0:42, saved, processing". Alternatively drop `aria-label` and use visually hidden text inside the link. Remove the `aria-label` from the heart span (keep it `aria-hidden`).

### I-7 Status changes are not announced: save, cover, uploads
- **Where:** `AlbumGrid.tsx:275` (the "Saved 3 to your favourites." / cover message span has no live region), :177 (the "n selected" count); `app/g/[token]/GuestUploader.tsx:78-92` and `app/(app)/UploadTray.tsx:31-44` (progress drawn as styled divs: no `role="progressbar"`, no live "All done" / "3 failed"); `Viewer.tsx:284-295` (Save toggle relabels to "Saved" with no `aria-pressed`). Attendee, photographer and organiser.
- **Heuristic / severity / effort:** WCAG **4.1.3 Status Messages** (AA); Nielsen #1 visibility of system status. **Sev 2**, effort **S**.
- **Problem:** A photographer using a screen reader uploads 200 files and is never told they finished or that 3 failed. An attendee who saves 12 photos hears nothing. Visible feedback exists; it just isn't exposed. Photographers are signed out and on their own, with nobody to ask.
- **Fix:** Wrap the AlbumGrid message in `role="status"`. Give both upload bars `role="progressbar" aria-valuenow aria-valuemin=0 aria-valuemax=100 aria-label="Upload progress"` (PlanMeters already does this, `components/PlanMeters.tsx:22`), plus a polite live region that speaks only on state changes ("All done", "3 failed"), not every percent. Add `aria-pressed={saved}` to the viewer's Save.

### I-8 The sign-in code boxes drop focus after a wrong code, and focus on a filled box is barely visible
- **Where:** `app/(auth)/signin/code/CodeForm.tsx:293` (`disabled={pending}` on every box), :218-224 (on error it calls `setPending(false)` and then `boxes.current[0]?.focus()` in the same tick, while the boxes are still disabled), :294-295 (`outline-none`, then focus = border ink→ember plus a 3px `--kb-ember-tint` halo). Attendee and organiser, `/signin/code`, mostly on a phone.
- **Heuristic / severity / effort:** bug + WCAG 2.4.3 Focus Order, 2.4.7 Focus Visible. **Sev 2**, effort **S**.
- **Problem:** Disabling the focused input blurs it, and iOS closes the keyboard during "Checking…". On a wrong code, `focus()` runs before React re-enables the boxes, so it silently fails. The user has to tap the first box again, and VoiceOver focus goes back to the top of the document. Typos in an 8-digit code are common, so this is a frequent path. Measured: once a box is filled, focus only changes its 1.5px border from ink to ember (**2.49:1** between the two states), and the halo is **1.18:1** on white. When moving with ← and →, you cannot see which box you are in.
- **Fix:** Use `readOnly` plus `aria-busy` on the group instead of `disabled`, or move the refocus into a `useEffect` that runs when `error` is set and `pending` is false. Use the house ring on the boxes (`outline: 2px solid var(--kb-ember); outline-offset: 2px`) instead of `outline-none` plus the tint halo. The same tint-halo pattern on `.input:focus-visible` (`globals.css:513-522`) passes AA but is the weakest focus state in the system.

### I-9 Caption grey fails on sand: every eyebrow on a sand section is 4.43:1
- **Where:** Token `--kb-ink-3: #6b6e76` (`app/globals.css:25`; its comment says "4.9:1 on white", which is true only on white; I measure 5.10). It fails on `--kb-sand #efefec`: `.kb-eyebrow` (`globals.css:243-249`) via `SectionHeading` (`components/site/parts.tsx:164`) on `.kb-sand` sections (Home "How it works" `components/site/Home.tsx:61-63`, Pricing "Every size" `app/(marketing)/pricing/page.tsx:99-102`, Features "Share kit" `features/page.tsx:39-45`), and the Enrol avatar placeholder text (`app/(app)/e/[handle]/me/Enrol.tsx:64`). It is also 4.48:1 on `--kb-warn-tint`. Organiser (marketing) and attendee (selfie step).
- **Heuristic / severity / effort:** WCAG **1.4.3 Contrast (Minimum)**. 14px text needs 4.5:1. **Sev 2**, effort **S**.
- **Problem:** Small grey labels on the alternate sections are below the minimum. The margin is small, but it is a hard fail on the page that sells the product, and the token is used in 40+ places, so the risk spreads wherever someone puts a caption on sand.
- **Fix:** Darken the token to `#66696f`: 4.78:1 on sand, about 5.5 on white, and visually the same. Fix the comment to give the worst-case ratio ("4.8:1 on sand"). Add a unit test next to `lib/theme` that checks every text token against `cream`, `sand`, `white` and both tints.

### I-10 Links told apart by colour alone (app landing, emails), and an email link at 3.97:1
- **Where:** `app/(auth)/signin/AppLanding.tsx:30-36` (Terms and Privacy Policy: `no-underline`, brand blue inside `--kb-ink-2` text; the two colours are **1.19:1** apart, and 3:1 plus a non-colour cue on hover/focus is needed). `emails/Layout.tsx:28-33` (footer links styled `#6b6e76`, the same as the surrounding text). `emails/AlbumPublished.tsx:27`, `emails/AccessEnding.tsx:26`, `emails/DeletionWarning.tsx:29` (unstyled `<Link>` inherits react-email's default `#067df7` with no underline: **3.97:1** on white at 14px, off-brand). Attendee in the iPhone app; all email recipients.
- **Heuristic / severity / effort:** WCAG **1.4.1 Use of Color** (A), 1.4.3; Nielsen #4. **Sev 2**, effort **S**.
- **Problem:** On the first screen of the app, the legal links read as bold words, not links. In emails, the unsubscribe and "Run your own event" links cannot be seen as links, and the unsubscribe link fails contrast. That matters because unsubscribe is a legal must-find.
- **Fix:** Underline inline links (the global `a` style already sets `text-underline-offset: 4px`, so just drop `no-underline` in running text). In `emails/Layout.tsx`, add an `emailStyles.link = { color: "#1f379b", textDecoration: "underline" }` and use it for every inline `<Link>`.

### I-11 Keyboard input does the wrong thing in the viewer and the selection bar
- **Where:** `Viewer.tsx:151-161` (the window keydown handler only skips `input` and `textarea`); `AlbumGrid.tsx:200-210` (Download is an `<a aria-disabled>` with `pointer-events-none`); `app/api/albums/[id]/zip/route.ts:19,42` (an empty `only=` falls through to `range(part…)`, the whole first part of the album). Attendee, viewer and album selection.
- **Heuristic / severity / effort:** bug + WCAG 2.1.1 Keyboard, 4.1.2. **Sev 2**, effort **S**.
- **Problem:** (a) With a video focused, ← and → should seek. Instead they jump to the previous or next item, and Escape leaves the album, so keyboard users cannot scrub a video. Alt+← (browser Back) also fires a `router.replace`, because modifier keys are not checked. (b) `pointer-events-none` only blocks the mouse. A keyboard user who tabs to the "disabled" Download with nothing selected and presses Enter downloads the entire first zip part of the album, not nothing.
- **Fix:** (a) Return early if `e.defaultPrevented || e.altKey || e.metaKey || e.ctrlKey`, or if `e.target` is inside a `video`, `button`, `a` or `[role=dialog]`. (b) Render `<button disabled>` when `selected.size === 0`, and have the zip route return 400 for an empty `only=`.

### I-12 Reduced motion leaves the swipe hint on every photo, and the landing depends on a native class being removed
- **Where:** `app/globals.css:1154-1161` (`.soft-hint-fade { animation: none }` under reduced motion, so the hint stays at full opacity), `Viewer.tsx:248-254` (shown until a *swipe* is recorded). `globals.css:1264-1281` (`.kb-rise` uses `both` fill-mode and is `paused` at its `opacity: 0` keyframe while `html.kb-splash` is set) and `ios/KlubbiesEvents/WebViewController.swift:95,121`. Attendee on a phone; iPhone app first run.
- **Heuristic / severity / effort:** WCAG 2.3.3 (AAA, but the product promises it), 1.4.13-adjacent obstruction; Nielsen #8. **Sev 2**, effort **S**.
- **Problem:** A Reduce Motion user who taps the arrow buttons instead of swiping never sets `kb-swiped`. "Swipe for the next one" then sits over the bottom of *every* photo for good. Separately, the landing's whole content is held at opacity 0 until Swift's `evaluateJavaScript` removes `kb-splash`. If that call misses the current document (for example, a redirect that commits after `hideSplash()` but before the user script list is cleared), the sign-in screen stays blank. (Good: the shimmer, pulse, rise, ping and native splash all respect reduced motion. This is the one gap.)
- **Fix:** Keep the fade under reduced motion, since an opacity change is not motion (`animation-duration: 0.01ms; animation-delay: 4s`), or hide the hint after any navigation, not only a swipe. For the landing, add a web-side fallback: `setTimeout(() => document.documentElement.classList.remove('kb-splash'), 9000)` in `AppLanding`, so the page never depends on one native call.

### I-13 Touch targets under the product's own 44px rule
- **Where:** `components/EventSwitcher.tsx:25` (`!h-9 !w-9` = **36×36**, in every event header including phones); `SettingsForm.tsx:81,99` (**32×32** swatches and colour input); `.kb-icon-btn` **40×40** with no `pointer: coarse` bump (`globals.css:440-452`), unlike `.btn-ghost` and `.btn-sm`; `.kb-menu-item` **40px** (`globals.css:1066`); `.kb-jump` **36px** (`globals.css:1237`). Attendee header on a phone; organiser settings.
- **Heuristic / severity / effort:** WCAG 2.5.8 Target Size (Minimum) **passes** (all ≥24px), but `docs/masterfile.md` §5 commits to "44px touch targets"; Nielsen #4. **Sev 2**, effort **S**.
- **Problem:** The event switcher sits next to the 44px avatar and the event name link, which is the most crowded part of the attendee header on a 375px phone, and it is the smallest target on the screen.
- **Fix:** One `@media (pointer: coarse)` block: `.kb-icon-btn, .kb-menu-item, .kb-jump { min-height: 44px; min-width: 44px }`. Drop the `!h-9 !w-9` override and make swatches 44px on coarse pointers.

### I-14 ARIA patterns misapplied: "menus" without menu keys, buttons inside buttons, a fake phone read aloud
- **Where:** `components/MoreMenu.tsx:88-98` (`role="menu"` with no arrow, Home or End keys, and it stays open when Tab leaves it); `components/AccountMenu.tsx:35,40-50` and `EventSwitcher.tsx:32-33` (a `<span>` heading, `<form>`s and a scrolling `<div>` as direct children of `role="menu"`); `RosterImport.tsx:133-159` (a `role="button"` dropzone *containing* the "Paste a list instead" `<button>`, and Space is not prevented, so the page scrolls); `components/site/Home.tsx:56` / `parts.tsx:75-114` (`PhoneMock` is not `aria-hidden`, so a screen reader reads a fake "Product Summit 2026 … Download all, See all" UI); `Viewer.tsx` has no `<h1>`; `components/AuthShell.tsx:56` puts an `<h2>` before the page `<h1>`; `emails/*.tsx` set headings as `<Text>` (a `<p>`). All user types.
- **Heuristic / severity / effort:** WCAG 4.1.2, 1.3.1, 2.4.6; Nielsen #4. **Sev 2**, effort **M**.
- **Problem:** `role="menu"` tells screen-reader users to use the arrow keys, which do nothing here, and the menu stays painted over the page after Tab leaves it. Inside the dropzone, assistive tech treats a button's children as presentational, so the "Paste a list" button is unreachable or announced as part of "Drop the guest list". The marketing page reads a fake app aloud.
- **Fix:** Switch `MoreMenu` to the disclosure pattern (button with `aria-expanded`, panel with a list of plain links and buttons, close on `focusout`). It is simpler and honest, and lets the forms stay. Make the dropzone a `<label>` for the file input and move "Paste a list instead" outside it. Add `aria-hidden` (or `role="img"` with a one-line label) to `PhoneMock` and `PosterMock`. Give the viewer a visually hidden `<h1>` (album title). Use react-email's `<Heading as="h1">` in the emails.

### I-15 Design-system drift: one-off buttons, colours, tokens and an off-brand error page
- **Where / evidence:**
  - Destructive confirms: `AlbumGrid.tsx:333-336` uses **`btn-primary`** for "Delete"; the other five destructive dialogs use `btn-danger` (`RemovalDecision.tsx:49`, `RevokeButton.tsx:26`, `MemberTable.tsx:289`, `AlbumEditPanel.tsx:220`, `BinView.tsx:191`).
  - Bespoke controls: the selection-bar pills (`AlbumGrid.tsx:181-249`, `bg-white/[0.16]`, `text-white/80`) and filter chips that override `.soft-btn` with five `!important`s (:266).
  - Semantics: an upload failure is drawn in the *event accent* (`GuestUploader.tsx:113,120`: `--color-accent-700`, `text-accent-800`), so on a green event "Failed" is green. Danger red `#b42318` is hardcoded in 10+ places with no `--kb-danger` token.
  - Token drift: `var(--kb-mist)` is used (`parts.tsx:15`) but never defined. Off-token greens `#1f6b3a`, `#245c2b`, `#2f6b36`, `#eaf5ea` (`ui.tsx:93`, `AlbumManager.tsx:47-50`, `GuestLinkForm.tsx:70`) sit next to `--kb-ok #1a7048`. Leftover plum rgba values `rgba(25,18,22,…)` and `rgba(43,34,40,…)` and the lightbox `#14100f` have no token.
  - Rule breaks: `FormMessage` uses `border-l-4` (`forms.tsx:35`) against the "No left border" rule. `UploadTray` is a square `border-2 border-ink` box (`UploadTray.tsx:31`) among 10px 1px-line cards. Text is set with opacity in 9 places (`text-white/80`, `/[0.68]`, …) against the house rule. `EventMark` initials fall to **11px** (`EventMark.tsx:35`) and sit white on the raw, unchecked event colour (:36).
  - Error page: `app/global-error.tsx:6-15` still uses the retired Klubbies salmon palette (`#fff8f4`, `#cf2e12`, pill button).
  - Theme: no dark mode, and nothing opts out of browser auto-darkening.
  - Organiser, attendee and photographer.
- **Heuristic / severity / effort:** Nielsen #4 Consistency and standards, #8 Aesthetic and minimalist design. **Sev 2**, effort **M**.
- **Problem:** Each item is small, but together they are why screens feel slightly different from each other. Two of them change meaning: a primary-styled Delete, and a green "Failed".
- **Fix:** Add `--kb-danger`, `--kb-danger-tint`, `--kb-lightbox`, `--kb-focus` and `--kb-scrim`. Replace the hex literals and define or remove `--kb-mist`. Use `btn-danger` in AlbumGrid's confirm and the danger token for upload failures. Extract a `SegmentedFilter` and a `SelectionBar` from AlbumGrid's one-offs. Restyle `global-error.tsx` with the current paper, ink and brand values (inline, since globals.css may not have loaded). Add `<meta name="color-scheme" content="light only">` (or `:root{color-scheme:light only}`) so Android's auto-dark cannot invert the UI while dark mode remains a deliberate non-goal. Add a lint rule banning `#[0-9a-f]{6}` and `text-white/` in `app/**` and `components/**`, outside `globals.css`.
