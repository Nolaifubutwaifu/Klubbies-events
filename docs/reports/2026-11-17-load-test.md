## Finding 1: photo access is checked per photo (critical, PR 41)

During the browse-only follow-up, 27 copies of `event_photographers()` were running at once in Postgres, up to 7.6 s each. That function and every album listing read `media` through `media_select`, which calls four SECURITY DEFINER helpers per row.

- One guest listing the 352 photo album: 407 ms on a quiet database, 7.7 s with 50 guests browsing. The statement timeout is 8 s.
- A 1,000 photo album at an event with 140 guests would time out for everyone.

PR 41 checks access once per query. Tested in a rolled-back transaction on production: identical results for 11 real users, 22.7 s down to 0.18 s in total, and the 352 photo listing went from 407 ms to 9 ms.

## Finding 2: sign-in bursts hit Supabase Auth's per-second limit

Raising the limits to 600 per 5 minutes (done 17 Nov) is not enough on its own. Supabase still refused 3 of 25 password sign-ins that arrived in the same second, all from Vercel's address (Auth sees every guest as the same IP). The code route (`verifyOtp`) runs into the same kind of limit.

What a guest sees: "That code didn't match" (or the password message). Their code attempt is also used up, because `verifyCode` counts the attempt before calling Supabase.

Options, cheapest first:
1. Retry on a Supabase 429 inside `verifyCode` and the password route (wait about 1 s, up to 3 times), and don't count a 429 as a code attempt.
2. Turn on Auth "IP address forwarding" and send the guest's IP, so each phone gets its own limit. Needs a code change to pass the header.

A real door rarely gets 25 people in one second, so this is lower risk than finding 1. Option 1 is a small change and worth doing.
