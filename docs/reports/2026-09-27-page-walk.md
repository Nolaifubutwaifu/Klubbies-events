# QA: every page against the masterfile, 27 Sep 2026

Walked locally against the seeded demo event (`pnpm demo`), as the organiser and as a new attendee who joined through the link, at 1440 px and at 375 px. Checked copy, layout, the access model and the design rules in masterfile sections 3, 5 and 6.

## Fixed in this pass

| Where | Problem | Fix |
| --- | --- | --- |
| Database | Attendees could rewrite their own membership row through the API (become organiser, undo a removal, move events); uploaders could un-hide a photo under a removal request | Update guards, migration 23 |

## Checked and working

* Access model: open-link joining with an email code creates an attendee; guest-list code requests answer neutrally; the access window closes galleries in RLS for attendees (0 of 14 photos visible after closing) while organisers keep all 17.
* Create an event (`/start`, code, `/admin/new`) to the setup checklist, activation, new album, upload with photographer credit, photographer link and its upload page, printable poster.
* Attendee event home, face notice then selfie invitation, album, viewer with filmstrip and actions, Your photos consent screen, Saved, profile with account deletion, Your events.
* Payment prompts are hidden inside the iPhone app (billing gate, banner, checklist, overview).

## Left as is, on purpose

* **Photographer album picker** (masterfile §6, `/g/[token]`): a link stays bound to one album. Letting a signed-out link choose any album would widen what a leaked link can do. An organiser makes one link per album instead. Recorded in `docs/decisions.md`.
* **Attendees table columns**: shows status, selfie and date added rather than "photos found". The per-attendee match count needs a service-role read of every attendee's matches; worth doing if organisers ask.
* **Price**: A$149 in `lib/copy/site.ts` is a placeholder until Max sets the price.
