# Decisions

Choices made while building Klubbies Events that `docs/masterfile.md` does not settle. Newest at the bottom. Klubbies' own history, which this product inherits, is in `docs/klubbies-decisions.md`.

## 2026-09-27 · Going live, and what came over from Klubbies

1. **The cloud database was built through the Supabase connector, not the CLI.** Every file in `supabase/migrations` was applied in order to project `yfdglvhhakbuahyfrihs`. The connector records each migration under the time it was applied rather than the file's own number, so the names in the cloud list match the files but the version numbers don't. Keep applying new migrations the same way, one file at a time, in order.
2. **Members and uploaders can no longer rewrite their own rows.** `authenticated` had table-wide update rights on `memberships` and `media`, and the "your own row" policies only checked whose row it was. Any attendee could have made themselves an organiser, undone their own removal, or moved their membership into another event through the REST API, and an uploader could un-hide a photo someone asked to take down. Klubbies has the same hole. `20260927000023_row_update_guards.sql` adds triggers: the service role passes, people who manage the event keep their rights, everyone else can only touch the columns the app writes for them (accept, decline, face notice; an uploader's finishing step).
3. **Push devices are migration 24, not 23.** The handoff suggested renumbering Klubbies' `…000022_push_devices.sql` to 23; 23 went to the security fix above, which had to land first.
4. **Deleting an account, for events.** The only organiser of an event that attendees have joined must make someone a co-organiser first. An event nobody else joined closes with the account and its photos are deleted (there is no subscription to cancel: events are paid once). An attendee who joined through an open link leaves that event's attendee list, because the organiser only had the address because they joined; an attendee on an imported guest list stays on it as "not joined yet", because the list is the organiser's.
5. **The iPhone app says `KlubbiesEventsApp/`.** Klubbies' app sends `KlubbiesApp/`. Neither string contains the other, so neither site mistakes the other app for its own. APNs defaults to the bundle ID `app.klubbies.events`.
6. **No payment prompts inside the app, anywhere.** The billing gate, the organiser banner, the setup checklist and the overview's "Needs you" all switch to a plain status inside the app. The billing page already did.
7. **Dates avoid Intl's short months everywhere**, including event date ranges ("30 Sep – 2 Oct 2026"), which Klubbies' fix didn't cover because Klubbies has no ranges. `tests/unit/format.test.ts` pins it.
8. **Rekognition collections:** `klubbies-events` in production, `klubbies-events-preview` for Vercel preview builds, `klubbies-events-dev` locally. All are covered by the existing IAM policy on `collection/klubbies-*`.
9. **Support email is `support@klubbies.app`**, shared with Klubbies. It is the address on the support page, the legal pages and the App Store listing.
10. **A photographer's link stays bound to one album.** The masterfile's upload page mentions an album picker. A signed-out link that could pick any album would widen what a leaked link can do, so organisers make one link per album instead (the Photographers page already allows several links per person).
11. **Settings has a danger zone: Delete this event.** It needs the event's name typed, deletes faceprints in AWS, then every file, then the row. It shares `lib/events/delete.ts` with account deletion and pages through large events rather than trusting one query to return every photo.
12. **The setup checklist has seven steps**: details, activation, logo and colour, who can get in (or the guest list import in guest-list mode), first album, photographers, and sharing, which counts as done once an attendee has joined.
13. **The iPhone app is its own project, `ios/KlubbiesEvents.xcodeproj`**, copied from Klubbies' last committed app (push, entitlements, account deletion) and renamed throughout, so Xcode never confuses the two. Bundle ID `app.klubbies.events`, display name "Klubbies Events", the site's ink tile as the icon, the site's paper and ink as the app's colours. `DEVELOPMENT_TEAM` is left empty for Max to pick.
14. **The QR scanner only opens event links.** `EventLink.joinURL` accepts `/e/<handle>` or `/signin?event=<handle>` on the Events host and rebuilds a clean `/e/<handle>` URL from it; anything else, including other pages on the same site, gets "That code isn't a Klubbies Events link." A poster can't be used to send someone to an arbitrary page. The site shows "Scan the event's QR code" only inside the app, on sign-in and Your events; in a browser the phone's camera app already does this.
15. **Simulator scan testing reads an image.** Debug Simulator builds with `KLUBBIES_EVENTS_QR_IMAGE` set decode that file through the same code path as the camera. Nothing of it exists in Release builds.
16. **The update guards ask the real database role, and run as the caller** (migration 25). Migration 23 asked the request's claimed role, which also caught trusted database functions acting for a user and sessions that reset their role but kept their claims. The face RLS tests found it. The guard functions are `security invoker`, because inside a `security definer` function the current role is always the owner and the check would pass everything.
17. **The end-to-end tests describe Events, not Klubbies.** Someone signed in who isn't in an event now sees its join screen (link mode is open to anyone with the link), never its albums, and can't sign a single photo. A guest-list event shows no join button, and a removed attendee can't rejoin through the link.
18. **No "photos found" count per attendee on the Attendees page.** The masterfile's table lists it, but it would show organisers a number derived from each attendee's faceprint, and the product's promise is that face search results are the attendee's alone. The table shows whether someone added a selfie instead.
19. **Mail for klubbies.app is received by Forward Email.** Apex MX records point at `mx1`/`mx2.forwardemail.net`, with an apex SPF that includes Forward Email. Resend keeps sending from the `send.` subdomain with its own SPF and DKIM, so the two don't overlap. Which addresses forward where (support@, appreview@) is set in the Forward Email dashboard.
20. **Emails reply to support.** Every email is sent from `events@klubbies.app`, which nobody reads, with `Reply-To: support@klubbies.app`. Server errors are emailed there too (`ALERT_EMAIL`, at most one per 15 minutes per error).

## 2026-09-28 · Recently deleted bin (retention handoff, phase 1)

The retention and pricing handoffs are `docs/handoff-retention-backups.md` and `docs/handoff-pricing-tiers.md`.

21. **The bin is migration 26 and pricing is 27.** The retention handoff numbered pricing first; Max asked for the bin to be built first, so the numbers swapped. Nothing depends on the order.
22. **A binned row is invisible to everyone through the API, organisers included.** The handoff asked for the check in `private.can_view_event_item`, but organisers never reach that function's guest branch, so hiding binned rows there alone would have left every organiser page, count and storage signature showing them. Instead each policy on `events`, `albums` and `media` refuses binned rows, a new `private.event_live()` is part of `is_event_member`, `event_perm` and `can_view_event_item`, and `can_contribute_to_album` refuses binned albums. Views are `security_invoker`, so album counts leave binned photos out on their own. The bin page, restore and purge read and write with the service role after the app has checked the person runs the event. `supabase/tests/bin_rls.sql` checks all of this and fails if the photo rule is weakened.
23. **An album takes its photos into the bin with the album's own timestamp.** Restoring the album brings back exactly those photos. A photo binned on its own before the album stays binned. A photo whose album is in the bin can't be restored alone: "Restore the album these were in first."
24. **A binned event is gone for everyone until it is restored.** Attendees, photographers and organisers alike get a not found page; photographer links say they're switched off; the join screen treats it as unknown. Any organiser of the event can restore it, or delete it now, from Your events, where it shows as "Deleted, restore until (date)". Organiser means the Organiser role, as for every other organiser right.
25. **Undo for 10 seconds.** Photos are put back where they were in the grid. An album or event delete moves to another page (albums list, Your events), so that page shows the bar when its address carries `?deleted=<id>` and the item was deleted in the last minute; the address is cleaned up when the bar goes.
26. **Typed confirmation stays** for albums and events, even with Undo, because an event delete takes the whole gallery offline for every guest at once.
27. **"Remove it" on an unfinished upload also goes to the bin.** One rule for every organiser delete is simpler to explain than an exception for broken files, and the bin empties itself.
28. **Faceprints of a binned photo stay until the photo is deleted for good**, so a restore needs no re-indexing. Guests can't reach the matches because the photo is hidden. The privacy page now says a faceprint goes when its photo is deleted for good, and that an organiser's delete waits 30 days first while a removal request is immediate.
29. **A removal request on a photo that is also in the bin still deletes it for good when it falls due.** Someone asked for it to go.
30. **Deleting your account deletes binned events you alone organise**, straight away and whatever their attendees: nobody else could restore them, so there is nothing to hand over.
31. **The hourly purge spends at most 60 seconds**, taking up to 10 events, 50 albums and 2,000 photos a pass, oldest first, so the face jobs after it keep their share of the run.
32. **Migrations are now tested on a local Postgres 16** with a small stub for Supabase's `auth` and `storage` schemas before they go near the live project. All 26 apply cleanly and `face_rls.sql` and `bin_rls.sql` pass.

## 2026-09-28 · Tiers, the free tier and limits (pricing handoff, phase 1)

33. **The pricing handoff was written from Max's strategy doc and six answers he approved** on 28 Sep (paused guests, overflow emails, the late price, the credit link, the usage view, the source field). It is `docs/handoff-pricing-tiers.md`. The strategy doc's "Decisions for you" said the guest limit is "10% grace, then new joins are refused"; Max confirmed the 2 day overflow window instead.
34. **The limits live in the database, not only the app** (migration 27). A media insert past `photo_limit` raises `KB001`; a guest joining past the window raises `KB002`. Both are serialised per event with an advisory lock, so two uploads or joins at the same moment can't both take the last place. The app turns the codes into plain messages. `supabase/tests/limits.sql` covers the edges and fails if the join guard is removed.
35. **An event stores `plan`, `plan_rate`, `guest_limit` and `photo_limit`.** The numbers live once, in `lib/billing/plans.ts`; the app passes the limits to `public.apply_event_plan` when an event changes plan. `custom` is for quotes over 1,000 guests (limits set by hand); `unlimited` is for events paid or comped before tiers, as they were sold.
36. **Existing unpaid events become Free** (50 guests, 200 photos). If one already has more than 55 guests nobody is paused, because its window never opened, but nobody new joins until there is room.
37. **A Free event can upload, add photographers and take guests without paying.** `canWrite` now takes the event and says yes for Free or paid; `private.event_can_write` says the same. The old single price is still what Checkout sells until tier checkout (phase 4), so a payment moves the event to `unlimited`, and so does comping it in development.
38. **Who counts as a guest:** an active attendee (the Attendee role) who has signed in at least once. Organisers, co-organisers and photographers never count; a guest list row counts from its first sign-in. Photos count while processing, so parallel uploads can't overshoot; failed uploads and the bin don't. A video counts as one minute until its length is known at the end of its upload, so a long video can take an event slightly past its allowance. That is accepted rather than failing a finished upload.
39. **The window opens with the join that goes past the included 10%** and refuses joins from the 48th hour exactly. Pausing happens at the next hourly pass after that, so a guest is paused up to an hour late, never early.
40. **Organisers are never refused by the guest limit.** Restoring a removed guest, re-importing a list or changing someone's role goes through; after the window has closed, the database re-ranks who is paused instead.
41. **Who is paused is decided by join order** (first sign-in, then row id). Removing an included guest lets the earliest paused guest in; restoring them pauses that guest again. Nobody can pause or unpause through the API, organisers included; only the rules and `apply_event_plan` do.
42. **Paused guests still see the event**, with "This gallery is full for now", but no albums or photos, and can't add photos to albums open to attendees. Face matching carries on for them.
43. **The join screen of a full event keeps its form**, with "This event is full right now. We've let the organiser know. If you've already joined, sign in as usual." A code is only sent to someone who has already joined. A guest list guest whose first sign-in lands when the event is full signs in but stays "not joined yet".
44. **Videos over 500 MB are refused**, in the browser and on the server. Before, they only got a warning.
45. **Once the event is full, the rest of an upload batch stops** with the same message, rather than each file failing one by one.
46. **Restoring from the bin can't take an event past its allowance**; restore says to delete something else first.
47. **Migration 27 turns on the Free tier**, and "We've let the organiser know" relies on the overflow emails in phase 4. So migration 27 should reach the live database together with phases 3 and 4, not on its own. Migration 26 (the bin) stands alone.

## 2026-09-28 · The R2 copy, and serving from it (retention handoff, phase 2)

48. **The bucket isn't made yet.** The Cloudflare connector reached an account where R2 isn't switched on ("Please enable R2 through the Cloudflare Dashboard"), and its bucket tool has no location hint setting, so it couldn't make `klubbies-events-backup` in Oceania anyway. It also can't tell whether that account is the separate one the handoff asks for. The code is built so that with no `R2_` settings every part quietly does nothing and everything is served from Supabase, as today.
49. **What is copied:** each original, its `thumb`, `display` and `poster`, and each event logo with its small mark, under the same paths as in Supabase. Not selfies, avatars or album cover images: the handoff lists originals, previews and logos, and covers are organiser uploads that can be chosen again.
50. **When:** after an upload finishes, once the response has gone (like face search). Files over 200 MB wait for the hourly pass. The hourly pass starts nothing it can't finish at a cautious 10 MB a second; a file that couldn't fit even in a whole pass, or a big one that has failed twice, is flagged for `pnpm backup-drain`, a local script with no time limit. After five failures the web app stops trying.
51. **The hourly job now shares its 300 seconds.** It stops starting work at 280 seconds: the bin gets up to 45, backups up to 70, and face search whatever is left, up to its old 240. Before, face search assumed it had 240 no matter what ran first.
52. **Every permanent file delete queues the R2 copy to go 30 days later**, because every one goes through `removeObjects`. That covers the bin purge and the 12 month expiry, as the handoff says, but also removal requests, account deletion and replaced logos. One rule is simpler, and it lets a wrong removal be undone within the month. The privacy page now says a copy at Cloudflare goes 30 days after the photo. If removal requests should delete the copy at once instead, that is a small change.
53. **The monthly safety net** runs on the first hourly pass of the 1st of each month, at 3am Brisbane time. It lists R2 by event folder and deletes the folders of events that no longer exist and have nothing still waiting in the queue. "Past its deletion date plus 30 days" joins it with the 12 month expiry.
54. **Full quality comes from R2 once a file has a copy there:** single downloads, album and "your photos" zips, and video playback in the viewer. Thumbnails and previews stay on Supabase. The check is the same as before: the person's own client must be able to read the row under RLS before a link is made. Links last as long as before (5 minutes for a download, an hour for video).
55. **Restoring files:** `pnpm restore-media --event <handle> [--album <id>] [--media <id>] [--confirm]` copies back every missing file of rows the database still has, rebuilds a missing photo preview from the original with the uploader's sizes, and takes the chosen items out of Recently deleted. It can't rebuild a video poster. If database rows are gone too, restore the database from Supabase's daily backup first.
56. **The R2 code is tested against a local S3 stand-in** (moto): a 40 MB multipart copy, reading back, listing folders, a presigned download keeping a non-English filename, and deleting. It hasn't met real R2 or the demo event; that waits for the bucket.
